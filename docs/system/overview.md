## Executive Summary

SAA 2025 Web is the event site for Sun* Awards 2025: a public Homepage with an event countdown and award teasers, an "Award System" (Hệ thống giải) browse page, and a Google-OAuth login gate that restricts the private area to `@sun-asterisk.com` accounts (`docs/development-roadmap.md:9`; `docs/system/permissions.md:33-39`). ## Key Design Decisions

### Decision 1: Domain-restricted Google OAuth with layered server-side verification and continuous session revalidation

**Context**: Only Sun* employees (`@sun-asterisk.com` Google accounts) may hold a session; every other visitor must be blocked both at first sign-in and on every later request, since a session, once issued, must not silently outlive a change in eligibility (`docs/system/permissions.md:33-39`).

**Decision**: `signInWithGoogle()` starts Supabase OAuth with a `hd: "sun-asterisk.com"` query-param hint (`src/app/login/actions.ts:26-32`) — pre-fill only, not an enforcement mechanism (`src/app/login/actions.ts` comment; `docs/system/permissions.md:35`). The actual gate is server-side, at the OAuth callback: `isAllowedEmail()` checks the domain with strict parsing (exactly one `@`, non-empty local part, case-insensitive compare) (`src/lib/auth/allowed-email.ts:24-37`), and `emailVerified()` independently requires both `user.email_confirmed_at` and the first identity's `identity_data.email_verified === true` (`src/lib/auth/email-verified.ts:9-20`) — either failing signs the session back out and redirects to `/login?error=domain` (`src/app/auth/callback/route.ts:39-42`). The post-login redirect target passes through `safeNext()`, which accepts only a same-origin, single-`/`-leading path and rejects protocol-relative, `://`-bearing, backslash-bearing, or raw/percent-encoded CR/LF/NUL values (`src/lib/auth/safe-next.ts:23-45`). Every subsequent request — not just the first — is re-validated by `proxy.ts` (Next.js 16's replacement for `middleware.ts`) via `supabase.auth.getClaims()`, explicitly never `getSession()`/`getUser()` (`src/proxy.ts:33-38,60-77`); `PUBLIC_ROUTES` is matched by exact equality plus a `/auth/` prefix exception only, deliberately never `startsWith` on the full list (`src/proxy.ts:4-16`).

**Rationale**: The `hd` hint alone does not block other domains — it only pre-selects an account in Google's picker — so enforcement has to happen server-side, and it has to happen twice: once at the callback (blocks a disallowed account from ever getting a session) and again on every request via `getClaims()` (blocks a session from outliving revoked eligibility, since Supabase's own guidance treats `getSession()` as untrusted and `getUser()` as an unnecessary network round-trip for this check) (`docs/system/architecture.md:27-28`; `docs/system/permissions.md:41-43`). Splitting `isAllowedEmail` (domain-only) from `emailVerified` (identity-only) keeps two distinct security predicates from blurring into one under-specified check (`src/lib/auth/allowed-email.ts:1-12`).

### Decision 2: Profile row provisioned by a security-definer database trigger, not application code

**Context**: Supabase's own `auth.users` table has no concept of the app's `role` (admin/member) field; a `public.profile` row must exist for every account, created exactly once and consistently regardless of which code path produced the `auth.users` insert (`supabase/migrations/20260828000000_create_profile_table_and_trigger.sql:1-7`).

**Decision**: `handle_new_user()`, a `security definer` Postgres function with `search_path` pinned to `public`, is triggered `after insert on auth.users` and inserts the matching `public.profile` row (`id`, `full_name`, `avatar_url`) directly from `raw_user_meta_data` (`supabase/migrations/20260828000000_create_profile_table_and_trigger.sql:34-52`). No application code path (OAuth callback included) writes to `profile` directly. `role` defaults to `'member'` via a `check` constraint (`admin`/`member` only) (`supabase/migrations/...sql:8-15`), and RLS on `public.profile` carries exactly one policy — `profile_select_own` (`auth.uid() = id`), granted to `authenticated` only, with no insert/update/delete policy (`supabase/migrations/...sql:17-28`).

**Rationale**: `security definer` is required because the calling role (whatever inserted into `auth.users`) has no insert grant on `public.profile`; running the insert as part of the trigger keeps profile creation atomic with account creation itself, independent of which auth path (currently only Google) produced the row (`docs/system/architecture.md:21-23,29`). Omitting an insert/update policy is a deliberate YAGNI call — there is no self-service profile edit yet, and admin promotion is a manual/dev-seed-only operation (`docs/system-architecture.md:155`; `docs/system/permissions.md:14,18`).

## Security Overview

- **Authentication**: Google OAuth 2.0 exclusively, via Supabase Auth (`@supabase/supabase-js` + `@supabase/ssr`, `package.json:16-17`). No password, magic-link, or other provider is wired in the scanned source. Sign-in starts server-side (`src/app/login/actions.ts:21-40`); the OAuth code is exchanged for a session at `src/app/auth/callback/route.ts:31-32`; sign-out clears every `sb-`-prefixed cookie and calls `supabase.auth.signOut()` (`src/app/auth/sign-out/route.ts:33-41`). Session validity is re-checked every request via `getClaims()`, never a cached/trusted session object (`src/proxy.ts:60`).
- **Authorization**: Two roles only — `member` (default on first sign-in) and `admin` (`profile.role`, `check` constraint) — with no admin-only route implemented yet in this scan (`docs/system/permissions.md:10-13,27,45-47`; `supabase/migrations/...sql:13`). Enforcement is two-layered: route-level via `proxy.ts`'s allow-list (everything except `/`, `/login`, and `/auth/*` requires a session) (`src/proxy.ts:4-16,64-70`), and data-level via Postgres RLS's single `profile_select_own` policy — a signed-in user can read only their own profile row, never another's (`supabase/migrations/...sql:22-28`; `docs/system/permissions.md:16`).
- **Data Encryption**: Not configured in application code observed in this scan — no custom at-rest or field-level encryption logic exists in `src/**` or `supabase/migrations/**`. Encryption at rest and in transit for the database is a Supabase-platform concern outside the scanned source tree; the app's local dev config points at Docker-hosted Postgres (`docs/system-architecture.md:9-18`), and no production TLS/KMS configuration file was found in the File Inventory (`scout-report.md:19-97`). Flagged as a gap for downstream security review, not asserted.
- **API Security**: Server Actions get Next.js's built-in same-origin protection for free; the one Route Handler that performs a state change (`POST /auth/sign-out`) adds its own explicit `Origin` header check, rejecting a mismatched cross-origin request with `403` (`src/app/auth/sign-out/route.ts:27-31`). The post-login redirect is closed against open-redirect via `safeNext()` (`src/lib/auth/safe-next.ts:23-45`). At the build-tooling level, `eslint.config.mjs` enforces an import boundary forbidding `src/**` from importing `e2e/**`, specifically to keep the Supabase service-role key used by E2E fixtures out of the app bundle (`scout-report.md:217-219`).

## Scalability

- **Current Capacity**: The scanned configuration targets local development only — Supabase runs in Docker (Postgres on `54322`, Auth/API on `54321`) per `supabase/config.toml` and `docs/system-architecture.md:9-18`. No production deployment manifest, container orchestration config, or CDN/edge config was found in the File Inventory (`scout-report.md:19-97`), so current production capacity is not established by this codebase and is out of this document's scope to assert.
- **Scaling Strategy**: The app tier is stateless by design — `proxy.ts` re-validates each request independently via `getClaims()` with no server-side session store (`src/proxy.ts:40-58`), and React Server Components/Server Actions push most rendering to the server without a persistent per-request connection pool held in application memory. This shape is horizontally scalable at the app tier without sticky sessions. The data/auth tier scales independently as Supabase-managed Postgres + Auth, decoupled from the app process (`package.json:16-17`; `docs/system-architecture.md:9-18`). No autoscaling policy, connection-pooling config (e.g. PgBouncer tuning), or CDN/static-asset strategy beyond Next.js defaults was found in the scanned source.
- **Performance Targets**: None defined in the scanned source or docs — no Lighthouse/performance-budget config, SLA document, or load-test artifact was found in the File Inventory (`scout-report.md:19-97`) or `docs/development-roadmap.md`'s success metrics (`docs/development-roadmap.md:14-18`, which cover visual/functional parity and test-gate greenness, not latency/throughput).
